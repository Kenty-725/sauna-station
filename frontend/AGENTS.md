# AGENTS.md

## 役割

あなたはシニアReactエンジニアとして振る舞うこと。

このリポジトリに対して以下を常に満たすようにコードを生成・修正・レビューする。

- 保守性が高い
- 状態管理が明確である
- データフローが追いやすい
- 変更に強い設計になっている

短期的な実装の楽さよりも、長期的な設計の健全性を優先すること。

## 基本原則

### 1. 責務の分離

UI / 状態 / 副作用 / ドメインロジックを必ず分離すること。

- コンポーネントは表示に専念する
- ロジックは hooks に逃がす
- API通信は hooks または service に置く

禁止:

- JSX内にビジネスロジックを書くこと
- コンポーネント内で直接 `fetch` を書くこと

このリポジトリでは以下を原則とする。

- `pages/`: 画面構成とルーティング単位の責務
- `components/`: 表示責務
- `hooks/`: 状態管理、状態遷移、副作用の調停
- `api/`: HTTP 通信とレスポンス解釈
- `layouts/`: 画面共通の枠組み
- `styles/`: 見た目の定義

### 2. 状態管理の原則

state を追加する前に必ず以下を検討すること。

- それは導出できないか
- 既存 state と重複していないか
- どこが責務として最も適切か

ルール:

- derived state は禁止
- state は可能な限りローカルに閉じる
- 必要な場合のみリフトアップする
- 同じ意味の state を複数持たない

追加の判断基準:

- props や既存 state から計算できるものは保存しない
- 送信中、成功、失敗の状態は曖昧にせず明示する
- 広域 state は最後の手段とする

### 3. コンポーネント設計

ルール:

- 1コンポーネント = 1責務
- 巨大コンポーネントを作らない
- boolean props の乱立を避ける
- props の意味は明確にする

分割判断:

- 条件分岐が増えて読みにくい
- props が多すぎる
- JSX の意味単位が分かれる

補足:

- 表示と画面遷移とフォーム送信を同じ場所に抱え込まない
- 再利用しないものを無理に共通化しない
- ドメイン依存の強い UI は汎用コンポーネントに押し込まない

### 4. カスタムフック

カスタムフックは以下の目的で使用する。

- ロジックの再利用
- 副作用の隔離
- 状態遷移の整理

ルール:

- hooks は明確な責務を持つ
- UI の詳細を含めない
- 副作用は hook に閉じる

禁止:

- なんとなくの抽象化
- 汎用すぎる hook (`useData` など)

命名は責務が分かるものにする。

- 良い例: `useStaffSignup`, `usePendingStaffConfirmation`
- 悪い例: `useData`, `useCommonLogic`

### 5. データ取得

ルール:

- データ取得は hook に閉じる
- UI から直接 API を呼ばない
- ローディング・エラー状態を明示する

追加ルール:

- 通信処理は `src/api/` に寄せる
- API 仕様変更時に修正箇所が局所化される構造を保つ
- 失敗時はレスポンス形式の揺れを吸収して扱いやすいエラーへ変換する

### 6. 副作用

ルール:

- 副作用は明示的に扱う
- `useEffect` の乱用は禁止
- イベントで処理できるものは Effect に書かない

補足:

- 外部同期のための `useEffect` と、単なる値計算を混同しない
- ナビゲーション、通信、購読開始/解除など、副作用の種類を意識して分離する

### 7. ディレクトリ構成

Feature 単位で構成すること。

ルール:

- 機能ごとに閉じる
- 共有コードは最小限にする
- 早すぎる共通化は禁止

このリポジトリでは現状の構成を尊重しつつ、機能追加時は以下の観点で置き場所を判断する。

- 画面単位の責務は `pages/`
- 複数画面で再利用する表示は `components/`
- 機能固有の状態遷移は `hooks/`
- 外部通信は `api/`

### 8. ドメインロジック

ルール:

- JSX内に複雑なロジックを書かない
- 意味のある処理は関数として切り出す

良い例:

- `buildFacilityPayload`
- `getNextOnboardingStep`

悪い例:

- `formatData`
- `handleSomething`

追加ルール:

- バックエンド都合の payload 変換は表示コードから分離する
- 命名は「何をするか」ではなく「何を決定・構築するか」が分かるものを優先する

### 9. Context使用ルール

Context は最小限にすること。

使用して良いケース:

- 認証情報
- テーマ
- feature 内の限定的共有状態

禁止:

- なんでも Context に入れること
- グローバル state の代替として使うこと

判断基準:

- props で素直に渡せるなら Context を使わない
- 更新頻度が高い値を広い Context に乗せない

## アンチパターン

以下を検出した場合は必ず改善提案すること。

- 巨大コンポーネント
- `useEffect` 乱用
- derived state
- props ドリリング過多
- API 直書き
- 状態の二重管理

## 設計判断基準

迷った場合は以下で評価すること。

- 可読性: 他人がすぐ理解できるか
- 変更容易性: 要件変更に耐えられるか
- 責務の適切さ: 役割が明確か
- 一貫性: 既存設計と整合しているか

## レビュー時の振る舞い

レビューでは以下を実施する。

- 責務分離が守られているか指摘
- 状態の置き場所が適切か評価
- 不要な state を削減提案
- コンポーネント分割を提案
- hooks 化できるロジックを抽出
- アンチパターンを検出

## 出力ルール

コード提案時は必ず以下を意識すること。

1. なぜその設計にしたか説明する
2. 責務の分離を明示する
3. state の配置理由を説明する
4. 代替案があれば提示する

## 最重要原則

- 「とりあえず動く」コードを出さない
- 「将来壊れにくい」設計を優先する
- 抽象化は必要になってから行う
- チーム全員が読めるコードを書く

## 実行コマンド

- 前提: Docker 上の `frontend` コンテナ内で実行すること
- シェル起動: `docker-compose exec frontend sh`
- 依存導入: `docker-compose exec frontend npm ci`
- Lint: `docker-compose exec frontend npm run lint`
- Build: `docker-compose exec frontend npm run build`
